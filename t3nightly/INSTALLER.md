# Hard installer: ssh-launch strays

A desktop client's ssh launcher (`packages/ssh/src/tunnel.ts`) starts its own `t3 serve` when it finds no server answering. If that happens while the installer has the service stopped, the launcher's server takes the T3 home lock, and neither the candidate nor the rollback can start. The installer reaps such a server inside the cutover window only (`install_strays.py`).

A process is reaped only when all of these hold: its pid comes from `<home>/ssh-launch/*/pid`, the marker says `managed`, it runs as the installer's uid, its argv names the target home, it started within 10 s of its pid file, and it either listens on the service port or owns the home lock. Lock ownership is SQLite's exclusive write lock on the shared byte range of `server-owner.sqlite`: the pid in `/proc/locks` on Linux, the `F_GETLK` holder on macOS. Neither query takes a lock. Each reap is recorded in the install receipt's `reapedSshLaunch`, at most three times per health phase.

Signals are bound to the checked process on Linux through a pidfd (`platformBinding: "pidfd"`). macOS has no process-bound signal. There the reaper registers a kqueue `EVFILT_PROC NOTE_EXIT` watch before checking identity, and skips the signal once that process has exited (`platformBinding: "kqueue-checked"`, with a `hard-reap-skip-exited` step whenever a skip happens). The remaining window lies between that poll and `kill(2)`: the process would have to exit, be reaped, and have its pid reassigned through a full wrap of Darwin's sequential pid space. The t3-nightly orchestrator accepted this as the macOS floor on 2026-10-29.

The maintenance backup can omit its database copy only when the host's manifest class allows binary rollback (`compatible`, `fork-additive`, or `rollback-proven` after its forced-rollback proof) and the live migration history matches. Other pre-cutover backups use a size- and disk-aware copy deadline.

A candidate server prunes runtime versions that nothing references and that are more than an hour old (`prunePinnedRuntimes` in `apps/server/src/cloud/pinnedRuntime.ts`), so the previous version can disappear while the candidate serves. Before cutover the installer keeps a copy of the previous runtime in `<home>/runtime/.rollback-runtime/` and restores it before a rollback activates it. Files are hard links where `runtime/versions` shares a filesystem with the store and plain copies where it does not (a state dir may be a symlink to another volume).

## Live admission

Every installer mode, IM/IL stage, desktop swap and Windows feed activation checks UTC admission. Admission is restricted to the minute beginning at 08:00Z or 18:00Z; an admitted cutover may finish later. `--override-reason "..."` records the reason in the install receipt and appends an override record to `~/.agent-rails/lanes/t3-fast-release/STATE.md`. The installer records the admission and timestamp once, then checks that recorded grant (maximum age two hours for live forward cutover) before mutation; it does not re-enter the one-minute window after staging/baseline checks. Recovery/rollback for that admitted run skips the age limit but still requires its admission record and exact candidate version match. Isolated sandbox operations and teardown have no admission age limit and still revalidate the private target identity. Graph stages delegate admission to their concrete installer, so an override is appended once.

After admission, live service-control, launcher-restart, update-RPC and installer-dispatch subprocesses receive `T3NIGHTLY_INSTALL_WINDOW=1` for the agent restart guard. Inherited marker values are discarded and rebuilt from the gate receipt; read-only modes cannot grant it, and isolated rehearsal commands do not need or receive it. The marker is a child-process environment value, never a persistent service setting.

Other-host dispatches, including forge, pc-wsl, Book and native Windows installers, use `install-window --host HOST --version VERSION --receipt FILE [--override-reason TEXT] -- COMMAND ...`. This gates dispatch before SSH or a native installer runs. Unix hosts also enforce admission in `install` itself. Native Windows and desktop-bundled servers keep their existing update mechanism.

Rehearsals are exempt only with all three: a private home, a non-live port, and a `t3-rehearsal-*` or `com.t3-rehearsal.*` service. `--rehearsal`, `--force-rollback`, `--restart-probe` and `--drain-proof` refuse live identities even with an override. `--live-home PATH` protects an additional configured live home; symlink aliases are resolved.

## Drain then stop

By-hand installs go through `t3nightly/install-by-hand` only, locally on `--host`. Supply `--version`, `--run`, `--reason` (exported as `T3_LIVE_RESTART_REASON`) and the evidence/artifact/RPC paths listed by `--help`. Hosts outside the graph, such as ax102, use `--receipt-host` for the manifest target identity. `--print` prints without running or writing; omit it to install. The shared IL command builder preserves host backup policy and selects `--hard --rpc-tree` with a 120-second drain. Install-window overrides still need the separate `--override-reason`.

`install --hard` requires the candidate/artifact manifests and a real `--chat-project`. Live installs need no rehearsal receipt, smoke verdict or forced-rollback proof; the artifact and manifest digests, the backup and rollback copy, automatic rollback and the post-install chat probe remain. Every install drains, stops the service and starts the candidate; there is no hot swap and the engine calls none of the old restart RPCs (`server.prepareRestart`, `server.abortRestart`, `server.importRestartHandoff`, `server.getRestartStatus`). The drain (`install_drain.py`) reads the running server's `orchestration_v2_projection_runs` read-only once a second and waits up to `--drain-s` (default 120, owned by `install_policy.DEFAULT_DRAIN_S`, 0 to 300; a live install needs at least 1) for runs in `preparing`, `starting` or `running` to finish. Runs in `waiting` never hold the drain. The stop follows whether or not the drain finished: the server's own restart continuation resumes each cut turn once on the new build. The `restart-drain` step and the receipt's `restartDrain` carry the same fields: `outcome` (`drained`, `timed-out` or `unreadable`), `drained`, `waitedMs`, `deadlineS`, `activeRunIds`, `cutRuns` and `waitingRuns`.

After public routing, a binary class whose new server advertises `serverSelfUpdate` and `serverHotSwap` swaps back through `server.updateServer` and keeps the database; otherwise it stops, restores the previous runtime and starts it, or the receipt requests forward repair. Only `restore-rollback` restores the database after routing.

## Independent service artifacts

Server-only updates preserve `runtime/launcher` bytes. Bootstrap/change requires `--launcher-artifact FILE`, checked with pin drift before stop and in dry-run: schema `t3nightly.launcher-artifact/1`, `runtimeDir`, `sha256`, and `protocol: 3`. Hot-swap launchers declare `hotSwapProtocol: 1` and `ingress` matching production `LauncherIngressConfig`. The watchdog restores last-known-good bytes/config; hard rollback restores captured service files.

`--connector-artifact FILE` pins the separate `__service-connector` supervisor. Its schema is `t3nightly.connector-artifact/1`, with `runtimeDir`, `sha256` and `protocol: 1`. A launcher artifact can supply the same supervisor bytes; their pins and units remain independent. Production renderers create `t3code-connector.service` or `com.t3tools.t3code-connector.service`. Identical pinned bytes do not restart it. `service-artifacts install|uninstall` manages its owned unit and keeps runtime bytes on uninstall. Connector configuration is server-owned; the engine neither reads nor prints its credential.

## Isolated rehearsal

`rehearse` installs with `--hard --rehearsal` in a private home. A restore-rollback candidate runs under the production launcher unit rendered from `--rpc-tree`. The held active turn stays running through the drain and the stop; on the candidate the harness requires exactly one run whose `restartContinuationOfRunId` is that turn, releases the gate, and waits for the continuation to complete with the original nonce, with no new user prompt on that thread. `--force-rollback` injects a failed acceptance after routing and proves the restore.

## Rehearsal disk budget

Older `rehearsal-hot-swap-*` homes are kept to at most two, including fault siblings. Under the retention lock, each creation first prunes unloaded, finished homes until at most one remains, then creates the new home. A recorded live process group, active reservation or loaded unit is never pruned; if those prevent the one-home limit, creation refuses before allocating a home. Every normal pass/failure finalization checks the sandbox service and connector are not loaded before deleting older homes and retained rollback bytes. In-progress reservations and unknown unit identities are held, never stopped. Evidence outside homes is preserved. A teardown failure is reported, but retention still runs. No `rehearsal-fast-*` path participates.

Each finalization appends `{at, deleted, kib, run}` plus kept/held details to `~/.agent-rails/lanes/t3-hot-swap-cutover/rehearsal-retention.jsonl`. Loaded or uncertain older homes can temporarily exceed the limit; their receipts explain why and a later finalization retries them.

Immutable runtime trees are hashed into `~/.t3nightly/rehearsal-runtimes/<sha256>` once per host. macOS version paths, launchers and connector bytes are APFS clones; Linux version paths are symlinks and launcher/connector trees use hardlinks. Rollback references retain immutable store bytes. Clone reference receipts protect their source digests from GC even though macOS version paths are real directories. Candidate archives are still signature-verified before entering the store; tree hashes detect content drift. After hot-swap finalization, unreferenced digest directories and seed snapshots are pruned under `.store.lock`. Retained-home runtime links and seed receipts protect shared entries. An active rehearsal reservation defers collection, so preparing/running siblings cannot lose their bytes. Every publish or seed reuse renews publication metadata under the same store lock; GC also protects entries published within the last 15 minutes, including service-artifacts bytes not yet linked to a retained home.

Sanitized seeds are read-only SQLite-backed-up into stable content-addressed snapshots, then APFS-cloned or reflinked into the private writable DB. macOS refuses if APFS cloning fails, never falling back to a full runtime or DB copy; Linux can copy only the DB, never hardlink it. `evidence/storage.json` records the actual runtime, launcher and seed methods. No live DB is used or changed. Teardown deletes each hot-swap home's scratch SQLite/DB files in the same finally path as waiter cleanup, after collecting integrity and rollback evidence. The shared immutable seed remains. Studio checks `df -k /` before preflight and again before home creation and refuses below 65 GiB free, recording the measured number.

## Review recovery boundaries

A hard-install candidate is marked routed only after its first serving check succeeds. Failure before serving stops any failed launcher and reactivates the retained old runtime. After serving, a binary class may roll back by launcher IPC or by maintenance stop/restore-runtime/start on an older launcher, keeping the DB; `restore-rollback` restores it as before routing.

Launcher watchdog recovery always attempts service start in a `finally` block, even if restoring LKG bytes fails; failed launcher/config evidence names are unique. Connector pins are written before activation, so failed activation remains uninstallable. macOS live connector plists use `~/Library/LaunchAgents`; Linux connectors are enabled at install and disabled at uninstall. Sandbox connector removal tolerates an already-unloaded connector, and main sandbox teardown still runs after any connector cleanup error.

Retention dispatch follows the rehearsal directory name: fast-release homes keep their existing base policy. Every candidate removal is resolved beneath its owning run before deletion, including nested rollback trees.

## Provider hold-process ownership

Rehearsal provider turns invoke the installed `runtime/rehearsal_waiter.py` helper, not an inline unbounded loop. Each waiter acquires its own POSIX process group and records PID, PGID, process-start identity, home, gate and deadline in the run's `gate-waiters/` directory. It exits when released, when its home disappears, when teardown closes registration, or after its 600-second deadline. `Sandbox.close()` always closes waiter registration and terminates only those recorded identity-matched process groups in `finally`, including a failed run or service teardown failure. `gate-waiter-cleanup.json` preserves the terminated or already-exited PID/PGID receipts outside the home.

## Headless macOS storage

macOS rehearsal home, artifacts, staging, seeds, evidence and RPC source/dependencies must resolve under internal `~/.t3nightly`. Runtime and RPC dependency symlinks resolving onto `/Volumes` and seeds containing removable-volume paths are refused before boot. Stage artifacts into the shared internal store first; version links stay internal. Service and connector PATH exclude removable-volume entries. Device SDK discovery and provider temporary/config directories are explicitly sandbox-local, overriding launchd manager environment paths. The macOS Codex home starts with file-only credential storage and no inherited project, plugin or MCP paths. Provider HOME/config/tmp are private to the rehearsal, avoiding shell snapshots and cwd inherited from the agent's external checkout. Production renderers still supply the launcher/plist and separate connector unit. No TCC grant or GUI interaction is part of rehearsal setup.

No long reader may open the live database while the service runs: a `sqlite3_rsync` reader once held a read for 70 minutes, pinned the WAL and stopped every write. Each pre-stop bulk read (stage copy, pre-drain seed or catch-up) is a low-priority child holding one read transaction that dies with the installer (`PR_SET_PDEATHSIG`) and aborts past `--offbox-copy-s`, its WAL limit (16 MiB; pre-drain up to 1 GiB) or, pre-drain, two failed or over-1 s serving probes; it retries after 60, 120 and 240 s (`--predrain-throttle`: in a `MemoryHigh=4G` scope), then refuses with nothing stopped. `--offbox` takes no read snapshot. The stage copy (refused under the stage floor) ships, then is deleted; a first ship with nothing to clone streams it through zstd.

On Linux, `--offbox HOST:<root>/<host>` (roots: `offbox_hosts.py`) with `--hard` keeps the database off the host. ax42 uses ax102 and `--offbox-stopped-ship`: drain-then-hard; the stopped database syncs to a clone of the newest verified replica, rollback restores from it; sync, check and restore must fit `--offbox-stop-s`. Otherwise hard takes no local rollback copy except under `restore-rollback`: after the stop it backs the stopped database up into `--offbox-stage`, checks `quick_check` and identity, and restores from that copy first. Before the stop it only clones a verified replica (no remote check if `verified.json` is under 24 h old) and refuses if copy and check would exceed `--offbox-stop-s`. A background reship re-verifies the copy and syncs the replica from it, retrying for 24 h (`offbox-replica-<version>.json`). A hold record (timer, boot unit, sweeps) deletes the copy 2 h into the candidate once no reship is pending, and keeps it loudly past 24 h (failed installs: 24 h). A `.part` is swept when no copy holds the stage lock. Other off-box installs `sqlite3_rsync` the live database to `<version>/rollback/statev2.sqlite`, seeded from a clone of the newest verified replica (`install_offbox_preseed` ships one ahead) for up to `--offbox-seed-s`. Before the stop they re-sync and refuse with nothing stopped when the timed catch-up plus remote `quick_check`, or the WAL at `--offbox-mib-s`, exceeds `--offbox-stop-s`, or local space cannot hold an in-place restore. A replica counts once a remote `quick_check` is `ok` (`verified.json`); retention keeps `--backup-keep` verified versions, drops unverified ones idle 24 h, and never fails an install. A hard rollback skips the restore only for a binary-rollback class whose schema and migration rows match the backup; a restore class always restores, from the local copy first. Studio keeps a checksummed at-stop copy; Linux restore-rollback installs without `--offbox` (forge, ax102, Owl) keep a pre-drain copy: seeded while serving, it refuses with nothing stopped if 2 timed catch-ups + 30 s exceed `--offbox-stop-s`; delta, verify (header page only) and identity run stopped within that deadline, quick_check and sha256 after the restart (`skipped-service-stopped` if it ends stopped), and rollback restores by delta. All installs drain and hard-install.

At-stop local backups use an APFS clone in the owning home’s `runtime/rollback-backups` only while that volume keeps 40 GiB free plus one database size for each clone that will exist there (the new copy and the kept predecessor on that volume), since a clone diverges toward a full database as the live database changes; otherwise, and on clone or verification failure, they fall back to a verified SQLite full copy at the configured backups root. New copies and prepare backups carry an owning-home `at-stop.json`. Retention spans every backup root of the home (the configured root, `runtime/rollback-backups` and the StudioExt install-data backups): before a new backup it keeps the newest one, so at most two exist during an install, and after an installed or current outcome it keeps only that install's copy (the newest one when the install took none), so one remains. An install that ends before its service stop or restart, by failure, exception, SIGTERM or SIGHUP, removes the backup it took this run, marked or not; once the stop or restart has begun, that copy is the rollback copy and is never removed by the run. Unmarked legacy copies are reported as `legacyKept` and never removed. Legacy deletion approval belongs at `~/.open-factory/approvals/alex-t3nightly-legacy-backup-delete.json`; this engine does not consume that approval. `python3 -B -m t3nightly.install_backup_retention --root BACKUPS` reports count and allocated size; APFS shared extent accounting requires volume df before/after. Hot-swap admission requires fresh idle host-local acquire-to-ready evidence and a host-local baseline; older validated-only samples require maintenance.

On macOS, before a live install takes `~/.t3nightly/installer.lock`, it waits up to 600 s for a flock on `~/.agent-rails/thread-memory/lock` and releases it at once, so a thread-memory run already reading statev2 finishes; later runs stop while the installer lock is held. The wait is skipped when the lock file is absent and logged as `thread-memory-wait`. After the stop, `lsof` on statev2 and its `-wal`/`-shm` must name no holder; otherwise the error and the `databaseQuiescence` receipt record list each holder's pid and command and the service restarts on the old version. That rollback, like a drain refusal (`restartDrain.stopRefused`), carries `retryable: true` in its record, the receipt and the stage outcome file. Launchd job and hold plists prepend `~/.cargo/bin` to the inherited PATH when it exists.

Startup qualification uses a private seeded warm child: the probe sends acquire and measures through the first successful environment response after commit. Baseline and candidate samples are independent and interleaved, three each. Evidence comes from the rehearsal on the executing host, must be at most 3600 seconds old and match the old runtime digest. The candidate allowance is the baseline median plus max(15%, 500 ms, baseline spread), capped by the launcher hold budget. Sampling waits up to 60 seconds for host headroom (Linux: at least 20% idle CPU; Darwin: load at most half the CPUs). Active sandbox turns do not prevent sampling. An unsupported baseline probe or insufficient headroom selects hard installation; the install receipt records the fallback reason. Rollback qualification uses the same old acquire-to-ready metric.

Rehearsal receipts require `engineHead` and measure `engineDigest` from the executing engine bytes, rather than copying the manifest claim.

## Backup calibration

Run `python3 -B t3nightly/install --calibrate --home ~/.t3 --state-dir ~/.t3nightly --backups ~/.t3nightly/backups` before maintenance on each host (use the installation's actual paths). This mode never controls the service or installs a version. It clones a consistent WAL snapshot onto the backup volume, or attempts a guarded copy with a two-second live-reader deadline; a large database without clone support can refuse rather than hold a long live read. Verification and full-copy throughput measurement read only scratch databases, which are removed even on failure. The host record in the installer state directory expires after seven days or a database size change beyond 25%; estimates record the selected rates and source.

Local stopped-work admission prices a proven APFS capture and same-volume restore clone at zero copy seconds. Successful clone capture retains both quick checks; normal rollback checks the backup and restored database and hashes the restored bytes once. Low-space in-place rollback additionally hashes the source before deleting the failed database. Identity/startup overhead retains the 30-second allowance. If a capture clone fails, the full-copy estimate must fit the remaining stopped-work budget before copying; otherwise capture raises before runtime activation and the hard installer's no-backup recovery restarts the old service. Restore clone failure can fall back to a deadline-checked full copy, preserving the failed database until verified publication.
