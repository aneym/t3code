# Hard installer: ssh-launch strays

A desktop client's ssh launcher (`packages/ssh/src/tunnel.ts`) starts its own `t3 serve` when it finds no server answering. If that happens while the installer has the service stopped, the launcher's server takes the T3 home lock, and neither the candidate nor the rollback can start. The installer reaps such a server inside the cutover window only (`install_strays.py`).

A process is reaped only when all of these hold: its pid comes from `<home>/ssh-launch/*/pid`, the marker says `managed`, it runs as the installer's uid, its argv names the target home, it started within 10 s of its pid file, and it either listens on the service port or owns the home lock. Lock ownership is SQLite's exclusive write lock on the shared byte range of `server-owner.sqlite`: the pid in `/proc/locks` on Linux, the `F_GETLK` holder on macOS. Neither query takes a lock. Each reap is recorded in the install receipt's `reapedSshLaunch`, at most three times per health phase.

Signals are bound to the checked process on Linux through a pidfd (`platformBinding: "pidfd"`). macOS has no process-bound signal. There the reaper registers a kqueue `EVFILT_PROC NOTE_EXIT` watch before checking identity, and skips the signal once that process has exited (`platformBinding: "kqueue-checked"`, with a `hard-reap-skip-exited` step whenever a skip happens). The remaining window lies between that poll and `kill(2)`: the process would have to exit, be reaped, and have its pid reassigned through a full wrap of Darwin's sequential pid space. The t3-nightly orchestrator accepted this as the macOS floor on 2026-10-29.

The maintenance backup can omit its database copy only when the manifest proves binary compatibility against the observed migration history. Other pre-cutover backups use a size- and disk-aware copy deadline. After routing, rollback is restricted to a compatible hot swap; the current database is never restored.

A candidate server prunes runtime versions that nothing references and that are more than an hour old (`prunePinnedRuntimes` in `apps/server/src/cloud/pinnedRuntime.ts`), so the previous version can disappear while the candidate serves. Before cutover the installer keeps a copy of the previous runtime in `<home>/runtime/.rollback-runtime/` and restores it before a rollback activates it. Files are hard links where `runtime/versions` shares a filesystem with the store and plain copies where it does not (a state dir may be a symlink to another volume).

## Live admission

Every installer mode, IM/IL stage, desktop swap and Windows feed activation checks UTC admission. Admission is restricted to the minute beginning at 08:00Z or 18:00Z; an admitted cutover may finish later. `--override-reason "..."` records the reason in the install receipt and appends an override record to `~/.agent-rails/lanes/t3-fast-release/STATE.md`. The installer records the admission and timestamp once, then checks that recorded grant (maximum age two hours for live forward cutover) before mutation; it does not re-enter the one-minute window after staging/baseline checks. Recovery/rollback for that admitted run skips the age limit but still requires its admission record and exact candidate version match. Isolated sandbox operations and teardown have no admission age limit and still revalidate the private target identity. Graph stages delegate admission to their concrete installer, so an override is appended once.

After admission, live service-control, launcher-restart, update-RPC and installer-dispatch subprocesses receive `T3NIGHTLY_INSTALL_WINDOW=1` for the agent restart guard. Inherited marker values are discarded and rebuilt from the gate receipt; read-only modes cannot grant it, and isolated rehearsal commands do not need or receive it. The marker is a child-process environment value, never a persistent service setting.

Other-host dispatches, including forge, pc-wsl, Book and native Windows installers, use `install-window --host HOST --version VERSION --receipt FILE [--override-reason TEXT] -- COMMAND ...`. This gates dispatch before SSH or a native installer runs. Unix hosts also enforce admission in `install` itself. Native Windows and desktop-bundled servers keep their existing update mechanism.

Rehearsals are exempt only with all three: a private home, a non-live port, and a `t3-rehearsal-*` or `com.t3-rehearsal.*` service. `--rehearsal`, `--force-rollback`, `--restart-probe` and `--drain-proof` refuse live identities even with an override. `--live-home PATH` protects an additional configured live home; symlink aliases are resolved.

## Hot-swap installation

`install --seamless` requires the candidate/artifact manifests, an isolated rehearsal receipt, `--rpc-tree`, and a real `--chat-project`. It calls `server.updateServer`, whose server-side self-update service requests the launcher over IPC. The bounded serving gate matches version and launcher update ID. Acceptance checks historical identities, a real chat reply and any desired managed T3 Connect link, including one unhealthy before installation.

Only launchd/systemd-user services advertising `capabilities.serverHotSwap: true`, with verified running launcher bytes, protocol-qualified ingress and an isolated measured candidate qualify. WSL additionally needs systemd-user and linger. The pinned ingress drain deadline must equal `--drain-s`; a different deadline requires a launcher maintenance update. The protocol currently allows at most 300 seconds. Unsupported hosts record `hot-swap-unsupported` and use drain followed by the maintenance installer. Migration flags, maintenance flags, startup over budget or a launcher change also require maintenance. The fast IM/IL nodes use this selector.

After public routing, the database is never restored. A failed acceptance can swap back only with explicit manifest compatibility and a qualified launcher; otherwise the receipt requests forward repair and preserves the current database. Pre-routing launcher trial recovery remains the launcher's responsibility.

## Independent service artifacts

Server-only updates preserve `runtime/launcher` bytes. A launcher change requires `--launcher-artifact FILE`: schema `t3nightly.launcher-artifact/1`, `runtimeDir`, `sha256`, and `protocol: 3`. Hot-swap launchers additionally declare `hotSwapProtocol: 1` and `ingress` matching the production `LauncherIngressConfig` contract. The engine keeps last-known-good bytes/config and a bounded watchdog restores that launcher on failure without reverting the current database.

`--connector-artifact FILE` pins the separate `__service-connector` supervisor. Its schema is `t3nightly.connector-artifact/1`, with `runtimeDir`, `sha256` and `protocol: 1`. A launcher artifact can supply the same supervisor bytes; their pins and units remain independent. Production renderers create `t3code-connector.service` or `com.t3tools.t3code-connector.service`. Identical pinned bytes do not restart it. `service-artifacts install|uninstall` manages its owned unit and keeps runtime bytes on uninstall. Connector configuration is server-owned; the engine neither reads nor prints its credential.

## Isolated hot-swap proof

`rehearse --hot-swap --rpc-tree TREE` uses the production service renderers, the launcher, `KillMode=mixed` and 90-second stop deadlines. It keeps an HTTP loop, reused keep-alive connection, resumable WS event cursor and real running/queued turns. JSON and Markdown receipts record refused connections, flip gap, served versions, persisted-event continuity and database integrity. A fallback is explicitly non-hot-swap evidence, not a zero-outage pass.

A rehearsal accepts target `--launcher-artifact` and `--connector-artifact`, remapping ingress to its sandbox endpoint. A first-launcher bootstrap keeps the legacy launcher for the old baseline and installs the target at the maintenance cutover. For true hot-swap proof, `--old-launcher-artifact` seeds an already-capable baseline launcher separately from the target artifact; the candidate manifest supplies its isolated startup measurement in `hotSwap.candidateMeasuredStartupMs`. It exercises a queue-capacity-plus-one HTTP burst and launcher crash recovery. `--inject warm-death` kills the real trial at its warm IPC milestone; `--inject post-flip` kills it before validation/routing. `--force-rollback` injects a failed acceptance after routing. The isolated Node preload supplies crash injection without changing signed executable bytes. Unsupported launchers refuse crash modes rather than inventing a rollback proof. True hot-swap/crash receipts require the server branch and qualified old/candidate builds; current older builds prove only the fallback.

## Rehearsal disk budget

Hot-swap runs keep at most two `rehearsal-hot-swap-*` homes, including fault siblings. Under the retention lock, each creation first prunes unloaded, finished homes until at most one remains, then creates the new home. A recorded live process group, active reservation or loaded unit is never pruned; if those prevent the one-home limit, creation refuses before allocating a home. Every normal pass/failure finalization checks the sandbox service and connector are not loaded before deleting older homes and retained rollback bytes. In-progress reservations and unknown unit identities are held, never stopped. Evidence outside homes is preserved. A teardown failure is reported, but retention still runs. No `rehearsal-fast-*` path participates.

Each finalization appends `{at, deleted, kib, run}` plus kept/held details to `~/.agent-rails/lanes/t3-hot-swap-cutover/rehearsal-retention.jsonl`. Loaded or uncertain older homes can temporarily exceed the limit; their receipts explain why and a later finalization retries them.

Immutable runtime trees are hashed into `~/.t3nightly/rehearsal-runtimes/<sha256>` once per host. macOS version paths, launchers and connector bytes are APFS clones; Linux version paths are symlinks and launcher/connector trees use hardlinks. Rollback references retain immutable store bytes. Clone reference receipts protect their source digests from GC even though macOS version paths are real directories. Candidate archives are still signature-verified before entering the store; tree hashes detect content drift. After hot-swap finalization, unreferenced digest directories and seed snapshots are pruned under `.store.lock`. Retained-home runtime links and seed receipts protect shared entries. An active rehearsal reservation defers collection, so preparing/running siblings cannot lose their bytes. Every publish or seed reuse renews publication metadata under the same store lock; GC also protects entries published within the last 15 minutes, including service-artifacts bytes not yet linked to a retained home.

Sanitized seeds are read-only SQLite-backed-up into stable content-addressed snapshots, then APFS-cloned or reflinked into the private writable DB. macOS refuses if APFS cloning fails, never falling back to a full runtime or DB copy; Linux can copy only the DB, never hardlink it. `evidence/storage.json` records the actual runtime, launcher and seed methods. No live DB is used or changed. Teardown deletes each hot-swap home's scratch SQLite/DB files in the same finally path as waiter cleanup, after collecting integrity and rollback evidence. The shared immutable seed remains. Studio checks `df -k /` before preflight and again before home creation and refuses below 65 GiB free, recording the measured number.

## Review recovery boundaries

A hard-install candidate is marked routed only after its first serving check succeeds. Failure before serving stops any failed launcher and reactivates the retained old runtime. After serving, a compatible binary may roll back by launcher IPC or by maintenance stop/restore-runtime/start on an older launcher; neither branch restores the DB. Incompatible post-routing state requires forward repair.

Launcher watchdog recovery always attempts service start in a `finally` block, even if restoring LKG bytes fails; failed launcher/config evidence names are unique. Connector pins are written before activation, so failed activation remains uninstallable. macOS live connector plists use `~/Library/LaunchAgents`; Linux connectors are enabled at install and disabled at uninstall. Sandbox connector removal tolerates an already-unloaded connector, and main sandbox teardown still runs after any connector cleanup error.

Retention dispatch follows the rehearsal directory name, not the `--hot-swap` flag: fast-release homes keep their existing base policy. Every candidate removal is resolved beneath its owning run before deletion, including nested rollback trees.

## Provider hold-process ownership

Rehearsal provider turns invoke the installed `runtime/rehearsal_waiter.py` helper, not an inline unbounded loop. Each waiter acquires its own POSIX process group and records PID, PGID, process-start identity, home, gate and deadline in the run's `gate-waiters/` directory. It exits when released, when its home disappears, when teardown closes registration, or after its 600-second deadline. `Sandbox.close()` always closes waiter registration and terminates only those recorded identity-matched process groups in `finally`, including a failed run or service teardown failure. `gate-waiter-cleanup.json` preserves the terminated or already-exited PID/PGID receipts outside the home.

## Headless macOS storage

macOS rehearsal home, artifacts, staging, seeds, evidence and RPC source/dependencies must resolve under internal `~/.t3nightly`. Runtime and RPC dependency symlinks resolving onto `/Volumes` and seeds containing removable-volume paths are refused before boot. Stage artifacts into the shared internal store first; version links stay internal. Service and connector PATH exclude removable-volume entries. Device SDK discovery and provider temporary/config directories are explicitly sandbox-local, overriding launchd manager environment paths. The macOS Codex home starts with file-only credential storage and no inherited project, plugin or MCP paths. Provider HOME/config/tmp are private to the rehearsal, avoiding shell snapshots and cwd inherited from the agent's external checkout. Production renderers still supply the launcher/plist and separate connector unit. No TCC grant or GUI interaction is part of rehearsal setup.
